# Feature Specification: Fix Parallel Defense Analysis

**Feature Branch**: `087-fix-parallel-defense-analysis`  
**Created**: 2026-06-18  
**Status**: Draft  
**Input**: User description: "Fix parallel defense analysis: isLocal detection always true, counter shows wrong numbers (18/4), analysis not saved to DB, UI not showing analyzed status after completion or refresh"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Analysis results persist after page refresh (Priority: P1)

A lawyer opens the defense memo page, clicks "تحليل جميع الدفوع" to analyze all defenses in parallel. After the analyses complete, they refresh the page. They expect to see all previously analyzed defenses still showing their analysis results with a "محلل" badge.

**Why this priority**: Without persistence, all analysis work is lost on page refresh, wasting AI credits and lawyer time.

**Independent Test**: Click "تحليل جميع الدفوع", wait for completion, refresh the page, and verify each analyzed defense shows its analysis content and "محلل" badge.

**Acceptance Scenarios**:

1. **Given** the defense memo page with 7 defenses (all saved in the DB with real GUIDs), **When** the lawyer clicks "تحليل جميع الدفوع" and all analyses complete, **Then** each defense's `AnalysisJson` column in the `Defenses` table is populated with the analysis result.
2. **Given** 7 defenses with 4 already analyzed (AnalysisJson populated), **When** the lawyer refreshes the page, **Then** the 4 analyzed defenses show "محلل" badge and their analysis content, and the 3 unanalyzed defenses show "تحليل" button.
3. **Given** the lawyer clicks on a previously analyzed defense, **When** the defense detail panel loads, **Then** the full analysis (introduction, factual basis, legal application, etc.) is displayed.

---

### User Story 2 - Correct defense ID sent to backend for analysis (Priority: P1)

When parallel defense analyses are submitted, the system sends the real defense GUID (from the database) to the backend, not `00000000-0000-0000-0000-000000000000`. This allows the backend to save the `AnalysisJson` to the correct defense record.

**Why this priority**: This is the root cause bug. Without the real defense ID, the backend cannot persist analysis results.

**Independent Test**: Submit parallel analyses, check backend logs to confirm each job receives a real defense GUID (not `Guid.Empty`), and verify `AnalysisJson` is saved in the database.

**Acceptance Scenarios**:

1. **Given** defenses generated by the AI (stored in DB with real GUIDs), **When** the lawyer clicks "تحليل جميع الدفوع", **Then** each parallel analysis request sends the real defense GUID (e.g., `58B8A8B1-3FA6-40DE-5033-08DECC9F0C7F`), not `00000000-0000-0000-0000-000000000000`.
2. **Given** a defense with a real GUID is submitted for analysis, **When** the analysis completes, **Then** the backend saves the analysis result in the `AnalysisJson` column of the corresponding `Defenses` row.

---

### User Story 3 - Accurate progress counter during parallel analysis (Priority: P2)

When parallel defense analyses are running, the progress counter (e.g., "3/7") shows accurate numbers. The counter does not inflate when the component re-renders or re-mounts.

**Why this priority**: Wrong counter numbers (e.g., 18/4) confuse the user and undermine trust in the system.

**Independent Test**: Click "تحليل جميع الدفوع" for 4 unanalyzed defenses, observe the counter goes from 0/4 to 4/4 without exceeding 4.

**Acceptance Scenarios**:

1. **Given** 4 unanalyzed defenses, **When** the lawyer clicks "تحليل جميع الدفوع", **Then** the progress panel shows "0/4", incrementing to "1/4", "2/4", "3/4", "4/4" as each completes.
2. **Given** parallel analysis is running (showing "2/4"), **When** the user navigates between defenses (causing component state changes), **Then** the counter does not increment beyond the actual number of completed analyses.
3. **Given** all 4 parallel analyses have completed (showing "4/4"), **When** the progress panel is still visible, **Then** it does not show a number higher than 4.

---

### User Story 4 - Defense cards reflect analysis status in real-time (Priority: P2)

As each parallel defense analysis completes, the corresponding defense card immediately updates from "تحليل" (Analyze) to "محلل" (Analyzed) with a green badge, without requiring a page refresh.

**Why this priority**: Real-time feedback is essential for the user to know which defenses are done.

**Independent Test**: Watch the defense cards during parallel analysis; each should flip to "محلل" as its analysis completes.

**Acceptance Scenarios**:

1. **Given** parallel analysis is running for 4 defenses, **When** the first defense's analysis completes (SignalR sends JobCompleted), **Then** that defense's card immediately shows "محلل" green badge.
2. **Given** all parallel analyses have completed, **When** the user clicks on any analyzed defense, **Then** the detail panel shows the full analysis content.

---

### Edge Cases

- What happens when the user clicks "تحليل جميع الدفوع" twice rapidly? The button should be disabled during submission.
- What happens if some analyses fail and others succeed? Failed analyses should show failure state, successful ones should show "محلل".
- What happens if the user clicks "تحليل جميع الدفوع" when some defenses are already analyzed? Only unanalyzed defenses should be submitted.
- What happens if SignalR disconnects during parallel analysis? The fallback polling should eventually fetch completed job statuses.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The frontend MUST send the real defense GUID (from the DB) when submitting parallel defense analyses, not `00000000-0000-0000-0000-000000000000`.
- **FR-002**: The `isLocal` detection in the parallel analysis thunk MUST check whether the defense ID starts with `local-` prefix, not compare `defenseId === clientDefenseId`.
- **FR-003**: The backend MUST save `AnalysisJson` to the `Defenses` table when the defense has a real GUID (non-empty `DefenseId`).
- **FR-004**: The parallel progress counter MUST derive completed/failed counts from actual job statuses, not rely on an incrementing counter that can double-count on component remount.
- **FR-005**: The frontend MUST fetch and display existing defense analyses from the database when the page loads or refreshes.
- **FR-006**: The defense card MUST show "محلل" badge when `explanationsCache[defenseId]` is populated, and "تحليل" button otherwise.
- **FR-007**: The `ParallelDefenseProgress` component MUST show accurate progress based on actual `defenseAnalysisJobs` statuses.

### Key Entities

- **Defense**: Represents a legal defense argument. Key attributes: Id (GUID), CaseId, DefenseTitle, BasisFromCase, Scope, AnalysisJson (nullable - stores analysis result).
- **AiJob**: Represents an AI processing job. Key attributes: Id, CaseId, StepType, Status, ResultJson, RunId. For parallel defense analysis, each defense gets its own AiJob with StepType='AnalysisDefense'.
- **defenseAnalysisJobs (frontend)**: Redux state mapping job IDs to AiJob objects for tracking parallel defense analysis progress.
- **parallelDefenseTracking (frontend)**: Redux state tracking parallel analysis progress: totalDefenses, completedCount, failedCount, defenseJobMap, isRunning.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After parallel analysis completes, 100% of analyzed defenses have non-null `AnalysisJson` in the database.
- **SC-002**: After page refresh, all previously analyzed defenses display their analysis content and "محلل" badge within 2 seconds.
- **SC-003**: The parallel progress counter never exceeds the total number of defenses being analyzed (e.g., never shows "18/4").
- **SC-004**: Each defense card updates to "محلل" within 1 second of its analysis job completing.
- **SC-005**: Zero AI credits are wasted due to analyses not being persisted (no need to re-analyze).

## Assumptions

- Defenses generated by GenerateDefenses step are already saved in the DB with real GUIDs (confirmed by investigation of `GenerateCaseDefensesAsync` method).
- The `GetDefenseAnalysisByDefenseId` endpoint already exists and works correctly for fetching individual defense analyses from the DB.
- The existing `hydrateStep` mechanism correctly populates `explanationsCache` when analysis data is provided.
- The `AnalysisDefense` bypass in `useAiJobSignalR.ts` and `aiJobsSlice.ts` (for `runId` filtering) is already in place.
- The staggering mechanism (3-second delay between parallel submissions) remains unchanged.
